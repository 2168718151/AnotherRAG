## 1. 先看结论和当前阻断

正常使用目标应是：

```text

```

当前实际还需要人工准备本地服务和进程环境。此前操作繁琐的原因包括：已有 PostgreSQL 连接文件未直接复用、服务未启动直到选库才报错，以及明确的 LLM 鉴权失败被笼统分类成 unknown。

服务状态会变化。以下地址来自本次本机配置，不等于这些服务此刻必然已经启动；启动前检查，正在运行的服务直接复用。

## 4. PowerShell：读取已有连接配置

在 PowerShell 中执行：

```powershell
Set-Location "D:/text_Project/Another RAG"

if (-not (Test-Path -LiteralPath "./data/postgres/session-url.txt")) {
    throw "缺少已有 PostgreSQL 连接文件，请先确认实例配置，不要猜填账号或密码。"
}

$env:STORY_RAG_POSTGRES_DSN = (Get-Content -LiteralPath "./data/postgres/session-url.txt" -Raw -Encoding UTF8).Trim().Replace("postgresql+asyncpg://", "postgresql://")
$env:STORY_RAG_POSTGRES_SCHEMA = "story_rag_manual_fatigue_20261026"
$env:NO_PROXY = (@($env:NO_PROXY, "127.0.0.1", "localhost") | Where-Object { $_ }) -join ","
```

注意：

- 连接文件里原来是 SQLAlchemy 驱动式 URL `postgresql+asyncpg://...`；当前 psycopg 使用 `postgresql://...`。上述命令只在内存中转换，不修改原文件。
- 本机保存的非秘密字段是：host `127.0.0.1`、port `55432`、dbname `story_sessions`、user `story_rag`。密码从文件读取，本文不记录。
- 上述赋值会覆盖此前填错的当前进程变量，不使用“变量非空就跳过”的逻辑。
- 这些环境变量只对当前 PowerShell 及之后从它启动的子进程生效。换一个终端后，需要重新执行本节。
- 不要用 `Get-Content` 或 `Write-Output` 单独打印连接文件、完整 DSN 或 API Key。
- 本节不再使用 `Read-Host` 逐行询问连接串，避免整块粘贴命令时把后续 PowerShell 代码误读为连接内容。

## 5. PowerShell：检查和启动 PostgreSQL

先检查项目现有实例：

```powershell
& "./tools/postgresql/17.11-5/pgsql/bin/pg_ctl.exe" -D "./data/postgres/cluster" status
```

若显示服务器已运行，跳过启动命令。只有明确显示 `no server running`，并确认仍使用本项目现有实例时，再执行：

```powershell
New-Item -ItemType Directory -Force -Path "./logs" | Out-Null

& "./tools/postgresql/17.11-5/pgsql/bin/pg_ctl.exe" -D "./data/postgres/cluster" -l "./logs/postgres_manual_test.log" -o "-h 127.0.0.1 -p 55432" -w start
```

可以再查看是否接受连接：

```powershell
& "./tools/postgresql/17.11-5/pgsql/bin/pg_isready.exe" -h 127.0.0.1 -p 55432 -d story_sessions -U story_rag
```

`pg_isready` 只说明服务是否接受连接，不能替代账号鉴权或迁移验证。若启动失败，先看 `D:/text_Project/Another RAG/logs/postgres_manual_test.log`；不要为解决启动问题删除 cluster、手动删除 PID 文件或重新执行 initdb。

## 6. PowerShell：检查和启动 Qdrant

先检查默认 HTTP 端口：

```powershell
Get-NetTCPConnection -LocalPort 6333 -State Listen -ErrorAction SilentlyContinue | Select-Object LocalAddress, LocalPort, OwningProcess
```

若没有监听，再执行项目已有启动脚本：

```powershell

```

成功提示类似：


若端口已有监听，不要重复启动；应检查该端口是否为预期 Qdrant 服务。可使用不读取代理环境的本地只读就绪检查：

```powershell
uv run python -c "import httpx; r=httpx.get('http://127.0.0.1:6333/readyz', trust_env=False, timeout=3); r.raise_for_status(); print('Qdrant ready:', r.status_code)"
```

启动脚本复用 `D:/text_Project/Another RAG/data/qdrant` 下的现有存储。本轮手测不需要新建知识库、重建向量或重新导入 TXT。

若脚本报告端口占用或启动失败，先停止后续步骤，查看 `D:/text_Project/Another RAG/logs/qdrant.stdout.log` 与 `D:/text_Project/Another RAG/logs/qdrant.stderr.log`，不要随意结束其他进程或删除存储。脚本会使用固定日志文件，重新启动前按需保留已有诊断记录。

## 7. 检查 LM Studio 与 LLM 配置

### 7.1 LM Studio Embedding

在 LM Studio 中确认：

- 本地服务端口为 `1234`。
- 加载的是 `text-embedding-qwen3-embedding-0.6b`。
- 服务器处于运行状态；仅打开 LM Studio 窗口不等于 HTTP 服务已启动。

可在 PowerShell 中只读查询模型列表，不调用生成：

```powershell
uv run python -c "import httpx; r=httpx.get('http://127.0.0.1:1234/v1/models', trust_env=False, timeout=3); r.raise_for_status(); print(*[m.get('id') for m in r.json().get('data', [])], sep=chr(10))"
```

模型列表可访问不等于完整 Embedding 请求一定成功；实际问答启动时还会进行 Embedding 维度探测。Reranker 会在应用需要时从现有本地路径加载，不需要在 LM Studio 中另开一个 Rerank 端点。

### 7.2 DeepSeek 配置与当前 401

模型名和 API Key 默认从 `D:/text_Project/Another RAG/api.txt` 读取；如果设置了 `API_FILE`，以实际指定文件为准。Base URL 默认来自项目配置，若设置了 `DEEPSEEK_BASE_URL` 则受该环境变量覆盖，不能假设只改 api.txt 就能改地址。

可先查看配置文件路径覆盖是否存在，不输出凭据：

```powershell
if ($env:API_FILE) {
    Write-Host "当前 API_FILE 路径：" $env:API_FILE
} else {
    Write-Host "使用项目根目录 api.txt"
}
```

需要编辑时，在本地打开实际文件，保留现有格式并核对模型名与有效 API Key。项目当前识别的格式示意为：

```text
deepseek = <有效 API Key，仅在本机填写>
model = <当前账户可使用的模型名>
```

上面是占位格式，不是可直接使用的配置，不应覆盖现有有效值。401 表示本次凭据未被服务接受，应核对 Key 是否有效、是否已撤销、是否混用了其他平台的 Key，以及服务地址是否匹配。没有进一步错误证据时，不武断认定其中某一项。

保存后需要退出并重新打开 CLI。当前客户端不支持配置热加载，编辑文件后留在旧 CLI 进程中继续问，可能仍使用旧配置。此处不自动发送远程模型探测请求，也不在写文档时产生新的模型调用。

## 9. 保存手动测试输出并打开 CLI

建议在配置输入完成之后记录终端输出，避免把输入凭据的过程收入记录。在 PowerShell 中执行：

```powershell
$testLog = Join-Path (Get-Location) ("logs/manual_fatigue_" + (Get-Date -Format "yyyyMMdd_HHmmss") + ".txt")
Start-Transcript -Path $testLog

```

Transcript 用于保存终端可见输出，不是完整 Prompt 或内部节点导出。不同终端宿主的原生程序输出记录可能存在差异，应核对测试文件是否包含完整回复。程序内部日志仍统一写入项目 logs 目录。上述日志不是可直接公开的材料，分享前应检查敏感内容。

CLI 使用不需要单独启动 FastAPI。首次问答可能包含 Reranker 加载等冷启动开销，不应拿它直接与热态请求比较。

## 10. CLI：选择“数据测试”并新建会话

以下命令输入到项目 CLI，不是 PowerShell。逐条执行，前一步成功再继续：

```text
db list
db use "数据测试"
db current
documents list
conversation create "机械疲劳耐久五轮手测_20261026"
```

注意：

- 如果 `db list` 返回 `[]`，只表示当前注册表没有可用命名库，不能把历史报告中的 collection 名直接当作已登记库名。
- `documents list` 应确认实际包含适合本轮疲劳耐久问题的机械问答资料。库名或 ready 标记不能证明语料覆盖充足。
- `conversation create` 会自动选中新会话；同名会话不是同一身份。每次全新五轮复测可以新建会话并记录返回 UUID。
- 需要继续原会话时使用 `conversation list` 和 `conversation use <实际 UUID>`，不是按名称恢复。
- 切库后会清空当前会话选择，需要重新选择与该库绑定的会话。

提示符应类似：

```text
story-rag[数据测试|机械疲劳耐久五轮手测_20261026|r0]>
```

`r0` 表示当前会话尚无成功提交的问答轮次。

## 11. 五轮测试的执行规则

本组保留用户原文，只讨论原理、证据和工程流程，不要求数值计算或公式推导。三个主题分别为通用疲劳耐久改进、具体量产总成的验证流程、另一台独立设备的开裂故障；前两个相关，第三个必须保持独立。

- 每轮只发送下面对应的一条完整 `ask`，等待输出结束，再执行 `question list`。
- 不添加 `--no-history`：本轮需要测试历史继承。
- 不添加 `--question`：本轮需要测试自然语言指代与同轮多个任务，不能用单个明确引用替代验收目标。
- 本组使用 `ask`，不是 `query`。`query "问题" --trace` 只做检索与最终模型输入预览，不生成自然语言答案。
- 若出现请求 failed 或 unknown，先保留现场并处理故障，不跳过该轮继续下一轮。
- 即使请求 succeeded，也要检查各题状态、回答覆盖和证据；不能只看 revision 或是否有一段输出。
- 每轮 items 数量可以因任务拆分方式不同而变化，不能固定要求每轮恰好三个 items；必须覆盖应更新的主线，且不串题。

### 11.1 第一轮：同时建立三条问题主线

```text
ask "我有三个问题想一起问，都只讨论原理、判断依据和工程流程，不需要计算或推导公式。预研样机变为量产设备时怎样提高传动系统疲劳耐久性？请区分结构设计、材料工艺、装配和使用维护各自能解决的问题，不要只回答换更好的材料或者把零件加厚。再看一个具体场景：We are preparing a motor-driven transmission assembly for mass production. The prototype runs normally on the bench, but we have not yet established a durability validation process. How would you plan component-level and system-level verification, collect failure evidence, and decide whether the design is ready for production? 另外，另一台独立设备的传动轴运行一段时间后出现裂纹，现场只反馈“shaft cracked，故障@@锟斤拷??”，还没有提供裂纹位置、断口、载荷、材料或加工记录。现在能确定是疲劳、过载、材料缺陷还是装配问题吗？请区分可以给出的排查方向和目前不能下的结论。"
```

回复后执行：

```text
question list
```

观察三个目标是否都被保留。故障主线应明确缺少资料，给出排查方向，保留待补事项或等效未决状态，不能直接确定根因。

### 11.2 第二轮：补充实际工况与制造装配离散

```text
ask "接着刚才关于提高疲劳耐久性的分析问一下：样机以前只在平稳负载下运行，实际用户却会频繁启停、正反转、偏载和急停，设备还会经历冷启动与连续运行后的温升；量产又存在加工尺寸、轴系对中、轴承预紧和润滑状态的离散。这些变化会怎样影响你刚才提出的改进优先级？为什么样机在台架上运行正常，不能直接证明量产后的疲劳耐久性合格？这些条件也适用于前面那个准备量产的传动总成，请同步修订耐久改进思路和验证计划，说明应补哪些工况与制造装配差异，但先不要给那台独立设备的开裂故障定性。"
```

```text
question list
```

观察新条件是否同时作用于通用改进和量产总成验证两条主线；不能传播成独立设备已发生对应异常的事实，也不能提前结束该故障的待补状态。

### 11.3 第三轮：加速试验与静强度证据的边界

```text
ask "针对你刚才的验证计划继续追问：如果为了缩短试验时间，直接把载荷提高、把启停变得更频繁，能不能把这样的结果当作实际使用寿命的证明？应该怎样判断加速试验有没有改变主导失效机理？再回到你上一轮对疲劳耐久性的解释，如果零件的静强度检查通过、仿真中没有出现屈服，是否就能认为疲劳问题已经解决？请说明这些证据分别能证明什么、不能证明什么，并同步修订前面的改进建议和验证计划。不要因为某个零件先坏了，就直接把它当成整套设备在实际工况下必然最先失效的位置。"
```

```text
question list
```

观察同轮多个追问是否都被处理，前两条主线是否同步修订；不能把静强度通过当作疲劳问题已解决，不能把加速试验结果直接当实际寿命证明，也不能转入计算任务。

### 11.4 第四轮：仅限制当前验证阶段的授权与资源

```text
ask "给刚才那个传动总成的首轮验证再补一个限制：目前只能使用现有样机，尚未获准更改设计或制造新零件，也不允许破坏性试验、超出既定安全边界的运行或者拆解关键组件；可以开展经批准的外观检查、装配记录核查、常规工况数据采集和具备实施条件的无损检测。Under these restrictions, how would you reorganize the first validation phase? 请明确哪些风险可以先排查，哪些结论必须留到后续试验才能确认，以及首轮完成后应该提交什么证据和后续验证申请。这只是当前验证阶段的资源与授权限制，不代表前面关于结构、材料工艺和疲劳机理的通用改进原则失效。"
```

```text
question list
```

观察是否仅修改具体量产总成的当前验证阶段。当前方案不得安排未获准的设计变更、新制零件、破坏性试验、越界运行或关键拆解；应区分可先检查事项和后续待验证事项，同时保留既有通用改进原则。

### 11.5 第五轮：仅为独立开裂故障补齐证据


## 12. 每轮怎么判断是否符合预期

下面是人工检查表，不是已经通过的结果，也不是要求模型使用固定措辞的标准答案。

| 轮次  | 应更新的主题                    | 应继续保留的边界               | 主要失败信号                        |
| --- | ------------------------- | ---------------------- | ----------------------------- |
| 第一轮 | 建立通用改进、具体验证、独立故障三条主线      | 独立故障资料不足，不能定性          | 只回答一题；忽略英文场景；从噪声猜故障原因         |
| 第二轮 | 通用改进和具体验证都继承真实工况与量产离散     | 独立故障仍未补证据              | 只更新一条相关主线；把运行场景当独立故障事实        |
| 第三轮 | 同时解释加速试验边界和静强度边界，并修订前两条主线 | 不进行计算；不把首次失效位置绝对化      | 漏掉一个追问；将静强度或加速试验当充分寿命证明       |
| 第四轮 | 只重排具体总成首轮验证流程             | 通用原理仍有效；独立故障仍独立        | 违反禁止试验限制；把暂时不能改设计解释为通用设计建议失效  |
| 第五轮 | 独立故障从待补转为基于新证据的分析         | 前一总成尚未完成验证；有限试验不证明无限寿命 | 找错历史题；混合两套设备；把“未记录过载”说成完全排除过载 |

还应区分三种不同问题：

1. 环境或远程调用失败：优先定位服务、身份、网络或接口，不计为答案质量通过。
2. 知识库覆盖不足：记录未命中的依据、源文档和题目，不能直接等同于历史关联 Bug。
3. 子题遗漏、条件丢失或对象串题：即使请求成功，也属于业务验收未通过。

正常连续提交时 revision 应从 0 到 5；revision 只反映成功提交次数，不能证明答案正确。不要把后来新建会话的五轮结果拼接成原会话一次连续通过。

## 14. 已遇故障的定位与处理

排查顺序：先看工作流部位，再看影响，最后看具体文件或日志。不要把所有故障统一归因为预算不足。

| 工作流部位             | 现象                                                           | 已知含义或核验方法                              | 处理顺序                                |
| ----------------- | ------------------------------------------------------------ | -------------------------------------- | ----------------------------------- |
| 连接配置 → psycopg 解析 | `invalid connection option "$env:STORY_RAG_POSTGRES_SCHEMA"` | DSN 混入了 PowerShell 命令；发生在数据库连接之前       | 按第 4 节重新读取已有连接文件，覆盖错误变量；无需删库        |
| PostgreSQL 服务连接   | 连接拒绝或服务未运行                                                   | 先看 pg_ctl status，再核对 55432 与指定 cluster | 只在确认未运行时启动现有实例；失败先查 PG 日志           |
| 选库 → Qdrant 存储打开  | `BACKEND_UNAVAILABLE`，日志为 Qdrant 502                         | 本次曾出现 6333 无监听、直连失败；502 本身不能证明一定是代理问题  | 检查监听与不经过代理的 readyz；恢复服务后重新选库        |
| 选库之后的命令           | `DB_NOT_SELECTED`                                            | 上一次 db use 未成功，后续读文档/建会话没有当前库          | 先使 db use 成功，不反复执行依赖命令或新建重复数据库      |
| 模型初始化 → Embedding | 1234 连接错误或 embeddings 502                                    | 本地模型服务或代理路径需要检查，不等于 DeepSeek 失败        | 检查 LM Studio server、模型与本地接口；以实际响应定位 |
| 任务规划 → 远程 LLM     | `HTTP 401`，外层却为 `PLANNING_CALL_UNKNOWN`                      | 本次是明确鉴权拒绝，被程序笼统分类 unknown              | 核对有效凭据和实际配置，重开 CLI，再处理原请求阻塞         |
| 会话提交/顺序保护         | 前一请求 unknown，后续不能继续                                          | 程序为避免重复执行和乱序提交保留了阻塞                    | 先查明原请求，不盲目重发；符合恢复条件后显式确认            |
| 用量展示              | `accounted_tokens` 很大，实际 usage 为 null                        | 可能是保守预算记账，不是供应商实际计费量                   | 分开记录 provider usage、估算与预留；不据此计算费用   |

常用日志位置：

- `D:/text_Project/Another RAG/logs/app.log`：请求摘要、HTTP 状态等。
- `D:/text_Project/Another RAG/logs/error.log`：部分未被内部处理的异常堆栈。
- `D:/text_Project/Another RAG/logs/llama_index.log`：LlamaIndex 日志。
- `D:/text_Project/Another RAG/logs/postgres_manual_test.log`：本次手动启动的 PostgreSQL 日志。
- `D:/text_Project/Another RAG/logs/qdrant.stdout.log`、`qdrant.stderr.log`：Qdrant 启动与运行输出。

当前规划异常在 Workflow 内被处理时，不一定进入 error.log；因此不能仅凭 error.log 没有新内容认定没有错误。需要把结果中的阶段、请求时间与 app.log 中的 HTTP 状态关联起来。

本次排查曾发生解析异常回显完整连接串的情况。本文不复制该异常或凭据；含凭据的原始工具记录必须脱敏后才能外发。修改凭据或清理记录是独立操作，本文未执行。

## 15. 本次 unknown 的具体解释及恢复

### 15.1 这条记录表示什么

本次会话：`4af9ba96-4bfb-4ddf-a49d-ff9e5c7ac9e0`。

本次异常 request_id：`b73bab4b-a79f-4b64-b428-4f282e6739f2`。

这两个 ID 仅用于定位本次已经发生的现场，不是以后测试固定使用的 ID，也不是创建新会话的参数。

| 字段                                                    | 本次解释                               |
| ----------------------------------------------------- | ---------------------------------- |
| `status=unknown`、`failure_code=PLANNING_CALL_UNKNOWN` | 任务规划调用出现被统一兜底的异常；日志进一步明确为 HTTP 401 |
| `revision=0`、`turn_sequence=null`、`result_refs=[]`    | 这一轮未成功提交题目版本，不能当作第一轮已完成            |
| `answer=""`、`items=[]`                                | 没有形成可返回的回答与逐题结果                    |
| `llm_calls=1`                                         | 记账为一次规划调用尝试，不代表成功生成                |
| `prompt_tokens=null`、`completion_tokens=null`         | 未取得供应商实际 usage                     |
| `estimated_prompt_tokens=20353`                       | 规划输入的保守估算上界，不是用户文字本身的准确 Token 数    |
| `reserved_output_tokens=8192`                         | 为规划输出预留的容量，不是实际已经输出                |
| `accounted_tokens=28545`                              | 20353 + 8192 的保守记账，不是实际消耗或账单       |
| `settled_tokens=0`                                    | 没有已结算的已知 usage，不能据此证明供应商费用一定为零     |
| `elapsed_ms≈508`                                      | 失败返回的整轮耗时，不是完整成功问答的性能              |

### 15.2 原因处理后再恢复

先修正第 7 节中的实际 LLM 配置，并退出旧 CLI、在同一已配置 PowerShell 中重新执行：

```powershell
uv run story-rag shell
```

在 CLI 中选择原知识库与原会话：

```text
db use "数据测试"
conversation use 4af9ba96-4bfb-4ddf-a49d-ff9e5c7ac9e0
```

只有确认仍是这条原请求、原会话 revision 未推进、没有提交结果，并核对本次 401 日志后，才执行：

```text
conversation recover b73bab4b-a79f-4b64-b428-4f282e6739f2 --acknowledge-unknown
```

当前恢复实现会把该 unknown 请求标为 failed，保留 `UNKNOWN_ACKNOWLEDGED` 与原结果未知标记，解除相应阻塞；不提交答案、不增加会话 revision、不自动重发请求，也不会覆盖原始失败事实。

随后重新发送第 11.1 节的第一轮 ask。普通 ask 会生成新的 request_id；不要显式复用旧的失败 ID 来期待重新调用。若已经恢复，再次执行恢复命令可能得到 `REQUEST_NOT_RECOVERABLE`，应先核对状态，不盲目重复。

对于真正的网络中断、断流等结果未知情形，不能把本次 401 的处理结论直接套用。需核对供应商或请求记录，避免重复调用和重复提交。

## 16. 后续应改善的使用体验：建议，尚未实现

本节记录改进方向，不代表本次已经改了代码，也不把拟新增命令写成现有能力。

| 工作流部位          | 当前问题                    | 建议改动                                              | 快速验收标准                               |
| -------------- | ----------------------- | ------------------------------------------------- | ------------------------------------ |
| 启动 → 配置加载      | 用户要手填已有连接信息，容易把命令粘进 DSN | 明确环境变量优先级；支持受控读取已有本地连接配置及必要的运行时 URL 转换            | 不显示密码；不改原配置；有效环境覆盖仍生效                |
| 启动 → 依赖检查      | 到选库或问答才发现服务没启动          | 提前分别检查 PG、Qdrant、Embedding 与本地模型路径；远程真实模型探测单独显式开启 | 分组件展示结果；默认检查不产生付费生成；失败时给下一步命令        |
| 本地服务生命周期       | 用户不清楚要启动什么，可能重复启动       | 区分已运行服务和项目受管实例；提供明确启动入口及复用逻辑                      | 不接管未知进程；不初始化新集群；不清库；不停止主线程共享服务       |
| 首次初始化          | 迁移与日常启动混在一起             | 清楚区分首次/升级迁移和普通使用，不盲目自动迁移其他实例                      | 首次提示目标实例/schema；普通问答不重复要求初始化         |
| 错误分类 → LLM 调用  | 明确 401 被统一包装为 unknown   | 保留脱敏的供应商状态与阶段，将明确鉴权拒绝作为确定失败                       | 401 显示鉴权失败，不进入不必要的 unknown 恢复流程      |
| 错误分类 → 真正未知结果  | 需要防止重复付费或重复提交           | 仅对确实无法确定结果的调用保留 unknown 及显式恢复                     | 不静默重发；请求幂等、revision 和证据提交边界保持有效      |
| CLI 输出 → 排错    | 通用错误迫使用户翻很长日志           | 展示服务名、阶段、错误码、请求 ID、日志位置与可执行下一步                    | 不打印凭据、完整 Prompt 或全部节点正文              |
| CLI 回归 → 日常可用性 | 自动化测试通过不等于首次启动可用        | 增加与实际命令入口一致的启动及故障回归                               | 覆盖缺配置、服务关闭、代理、401、unknown、重启续会话及正常五轮 |

可以考虑新增统一诊断入口；例如 `story-rag doctor` 只是拟议名称，当前没有实现，不要直接执行。目标是把用户常规操作收敛到“打开 CLI → 选库 → 选会话 → 提问”，而不是通过文档要求用户永久承担底层排错。

建议实施顺序：先修确定错误的分类与脱敏提示，再补配置与依赖检查，随后验证实际 CLI 五轮体验。是否修改产品代码、增加命令或改变服务管理策略，需要独立实施任务；本次只保存说明。
