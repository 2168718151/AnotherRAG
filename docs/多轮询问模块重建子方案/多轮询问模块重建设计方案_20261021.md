## 1. 结论、范围与关键调整

可以实现。建议保留现有知识检索链路，增加“子问题规划、稳定身份、对象条件、定向历史回读、逐题验证”五项能力。多轮上下文以子问题为中心，不建立聊天全文记忆库，不新增本地生成式模型。

本文将“一个新对话”理解为一个 `session`，其中可以有多条用户消息；每条消息是一个 `turn`。如果每条追问都创建一个完全隔离的新会话，追问将无法自然承接，因此不能把这两个概念混用。

| 用户设想                 | 判断                   | 建议处理                                              |
| -------------------- | -------------------- | ------------------------------------------------- |
| 输入、拆题、逐题检索、去重、整合答案   | 可实现，但去重要分阶段          | 检索前去除重复目标；检索后去重证据，同时保留每题到证据的映射                    |
| 查到历史就整合，查不到就回到基础流程   | 需要区分当前问题是否自足         | 自足的新问题正常检索；“第二个呢”这类缺对象问题不能靠检索猜对象                  |
| 题目长期保存，后续直接更新        | 当前视图可以更新，不能丢失修订关系    | 稳定题号不变，追加修订版本，更新当前版本指针                            |
| 只保存答案所在文档和分块，不保存答案正文 | 可以实现，但能力有明确损失        | 支持重新取证回答；不能保证重现上一条生成答案或其“第二点”                     |
| 每个新对话新建数据库           | 建议解释为逻辑隔离空间          | PostgreSQL 共用表按 `session_id` 隔离；不为每会话新建物理数据库或知识集合 |
| 低召回率就认为库内无答案         | 在线无法直接测得真正召回率        | 用校准后的证据不足判定，输出该项“无”，内部记录“本次未找到足够依据”               |
| 开启深度思考时流式写入同一个 JSON  | 可以流式接收，但全局共用文件存在串写风险 | 每次 API 调用使用独立内存缓冲；只把完整正文交给后续模块                    |
| 首轮不能被找不到上级问题阻断       | 必须保证                 | 首轮不执行历史父题匹配；逐题检查当前消息是否足够，允许部分澄清、部分回答              |

本文建议采用上述调整。其中“逻辑会话库”和“只存引用的能力边界”应在开发前明确接受；这里先给出完整可实施设计，不将建议记为已实现功能。

## 2. 项目现状与历史教训

### 2.1 当前工作流

V1.2 已有选库、TXT 管理、向量与 BM25 检索、RRF、CUDA Reranker，以及最终 LLM 输入组装。当前请求模型没有长期子题身份和会话修订信息。

现有 CLI `query` 是零生成调用的预览入口。新增多轮问答应使用独立 `ask` 命令，避免原来的检索预览突然产生 LLM 调用。

### 2.2 本方案针对的问题

| 工作流部位 | 历史现象及影响                         | 设计要求                       |
| ----- | ------------------------------- | -------------------------- |
| 首轮路由  | 自足问题包含 `their`，被误判为缺历史，后续轮次连锁澄清 | 不用追问关键词决定首轮是否可以执行          |
| 历史定位  | 任务存在于 PostgreSQL，但已被近期窗口截掉      | 先定向定位任务，再分配模型上下文预算         |
| 子题规划  | 公式、数值和格式要求被拆成重复任务               | 区分独立目标与同一目标的输出要求           |
| 条件重组  | 梯度改为 FP32 后，只有部分题更新，其他题仍用 BF16  | 条件归属于明确对象，统一修订，按依赖影响子题     |
| 证据分配  | 合并生成引用了其他题独占的节点                 | 共享证据池与逐题许可映射分开维护           |
| 模型调用  | 深度思考耗尽输出额度，结构化正文为空              | 显式选择思考模式，区分推理额度、正文额度与上下文容量 |
| 预算    | 生成完成后才发现门控放不下                   | 生成前检查生成与门控两个阶段的容量          |
| 回答质量  | 正确公式产生错误舍入，相关性门控放行              | 数值运算走可验证的确定性计算，不把相关性等同于正确性 |
| 请求恢复  | 确定失败被当成结果未知，永久占用会话              | 区分确定失败与未知结果，采用请求幂等和短事务     |

历史台账中的修复发生在实验分支，不意味着回到 V1.2 后这些修复已在当前主线生效。本文不直接整体移植实验分支。

## 3. 调整后的完整工作流

```text
当前消息 + session_id + request_id + expected_revision + 可选题目引用
  -> 校验会话与知识库身份，建立请求执行记录
  -> LLM 提取目标、当前对象、条件修改、格式要求和历史需求
  -> 初步分题检查：覆盖原始目标，合并明确重复项
  -> 首轮：只解析本消息内的对象和指代，不找历史父题
     后续轮：精确定位 / 定向召回历史子题，再读取权威记录
  -> 程序合并对象条件，区分更正、追加、比较和新问题
  -> 再检查子题等价性、目标覆盖、缺失输入和真实依赖
  -> 对可执行子题检索知识库；缺参项单独等待补充
  -> 证据去重、逐题证据映射、证据充分性判断
  -> 预算内生成分题结果，程序检查并逐题门控
  -> 按原目标顺序合并输出；不强制再调用一次总结模型
  -> 短事务提交子题版本、条件版本、证据引用和请求结果元数据
  -> 输出最终结果；必要时更新可重建的历史候选索引
```

一轮可以同时出现新问题、旧题补充、条件更正和待澄清项。分支以子题为单位执行，不能把整轮归成唯一的“追问”或“新问题”。

独立子题通常采用一次规划、一次合并生成、一次批量逐题门控。定位歧义、容量分批或真实依赖可能增加调用；不能承诺每轮固定三次。

## 4. 分题与重复校验

### 4.1 先保留目标，再处理噪声

“不重要语言 + 分散问题”可以作为输入特点，不能当成无损删除规则。用户的否定、单位、版本、对象、范围、语言及格式要求可能散落在句间。

例如“随便聊聊，别算激活，梯度其实是 FP32，前面的值都别改”中，只有闲聊可以忽略，后面三项都影响任务。处理时记录每个目标对应的原文片段；无关寒暄不进入长期业务记录。

LLM 输出的是候选计划。稳定 UUID、历史身份、数据库身份和提交状态由程序决定，模型不能自行声明可信身份。

### 4.2 如何判定本质相同

比较键至少包括：对象、所求目标、适用条件、时间或版本、答案维度、范围和依赖。句子相似度仅用于找候选。

| 两个候选目标                        | 处理                                    |
| ----------------------------- | ------------------------------------- |
| “AOF 有哪些缺点”和“说说 AOF 的不足”，条件相同 | 合并成一题，保留两个原文目标的覆盖关系                   |
| 中文问题与其英文同义复述                  | 验证对象与条件一致后合并                          |
| “AOF 优点”和“AOF 缺点”             | 保留两个必要维度，可放入一题的 `requirements`，不能丢掉其一 |
| “ZeRO 的分片原理”和“该配置每卡多少 GiB”    | 目标不同，分别执行；必要时共享对象条件和证据                |
| “给出公式、分项、总计，并改成表格”            | 通常是一道计算题的多个输出要求，不拆成四次重复计算             |
| “梯度 FP32 与 BF16 分别怎样”         | 两个比较分支，不因为只有一个词不同就合并                  |

建议校验顺序为：规范化后的完全等价检查、现有 Embedding 的批量候选比较、条件和目标规则检查、必要时一次批量 LLM 等价判断。模糊时保留独立目标，不能为降低任务数量删除要求。

可以复用现有 Embedding 服务，但不直接用“知识检索分数”证明两个问题等价。当前 Reranker 是查询与文档相关性工具，未经问题对标注集验证，不能充当问题同一性裁判。阈值必须用中文、英文和跨语言正反例校准，不写死一个任意余弦阈值。

去重后必须保留 `原始目标 -> 执行题目 -> 回答要求` 映射。多个目标映射到一个任务是允许的，任何目标无映射都应阻止进入生成或触发有限修复。

## 5. 历史定位与问题重组

### 5.1 有历史不等于必须使用历史

| 当前输入                 | 历史处理            | 后续动作                  |
| -------------------- | --------------- | --------------------- |
| “Redis AOF 有哪些缺点”    | 本句自足，可不加载旧任务    | 新建或显式续接同题后检索          |
| “第一轮第三题，配置补齐如下……”    | 按稳定轮次和题号精确读取    | 核验身份后更新该任务            |
| “刚才那个训练场景，梯度改成 FP32” | 定向定位训练对象及关联任务   | 更新对象条件，再执行受影响目标       |
| “第二个呢”且有多个列表         | 不用相似度 Top-1 猜身份 | 提出只针对该项的澄清            |
| 未找到旧任务，但当前输入提供完整新目标  | 可以独立创建新任务       | 不据此标记某个未知旧任务完成        |
| 显式引用不存在或其他会话的题号      | 返回明确引用错误        | 不静默改成另一个任务；同轮其他独立题可继续 |

定位优先级：可信显式引用、明确轮次与题号、唯一待补任务及最近相关对象、限定会话的关键词候选、必要时语义候选。语义候选必须回读 PostgreSQL 原始子题记录核验。

历史检索与知识检索分开。所有历史读取受 `session_id + database_id + storage_fingerprint + as_of_revision` 限制，先限定范围再召回，不先取全库 Top-K 后过滤。历史索引不可用时可回退 PostgreSQL 定向查询，不能跨会话兜底。

任务目录只给模型紧凑的候选摘要，不把全部历史塞入窗口。“当前窗口没有”只能表示未提供，不能解释为完整历史不存在。

### 5.2 重组模块必须明确的关系

| 关系              | 示例                | 版本及检索策略                            |
| --------------- | ----------------- | ---------------------------------- |
| `supplement` 补充 | “那套服务的层数是 32”     | 原题新修订，补缺参后重新检索                     |
| `replace` 更正    | “不是 RDB，是 AOF”    | 保留旧版本；新版本替换对象，旧证据失效                |
| `extend` 扩展     | “再解释它的恢复流程”       | 新目标关联旧题，获取新增依据                     |
| `compare` 比较    | “另外比较 FP32”       | 建立比较分支，不能覆盖现行 BF16 条件              |
| `format` 表达变化   | “按表格说明”           | 不把“表格”送去检索；按已知题意重新呈现，精确复用受正文留存策略限制 |
| `cancel` 取消     | “刚才第三题不问了”        | 标记取消并保留历史，不复用题号                    |
| `new` 新话题       | “换个话题，讲 React 闭包” | 新建题目，避免继承训练配置                      |
| `ambiguous` 歧义  | “把那个改为 2”         | 不修改任何已有值，聚焦询问对象和字段                 |

“更新问题名字”只更新当前规范题目视图。规范题目表达当前有效目标，不把历次问题全文不断拼接。原目标、修改来源和修订关系分别保存，避免标题越问越长。

### 5.3 梯度问题的专项设计

需要分离三个概念：训练对象 `train_a`、推理对象 `infer_b`、针对对象提出的各个问题。参数、梯度、优化器状态等条件属于对象；“解释原理”“计算分项”“是否满足预算”属于任务。

“仅梯度改为 FP32，其他保持不变”应转成 `train_a.gradient_dtype = FP32` 的单字段修改。程序继承其他字段及其原来源，不把“保持不变”伪造为当前轮提供了参数量、卡数等新数值。

| 项目                 | 修改前   | 修改后   | 处理                |
| ------------------ | ----- | ----- | ----------------- |
| 训练参数精度             | BF16  | BF16  | 保持原来源             |
| 训练梯度精度             | BF16  | FP32  | 新来源明确指向当前更正片段     |
| 梯度字节数              | 2     | 4     | 根据受控精度映射派生，记录依赖   |
| master weights、m、v | FP32  | FP32  | 保持，不新增常驻副本        |
| 同训练对象的公式与数值任务      | 基于旧配置 | 基于新配置 | 标记受影响；要求同步更新时一起重算 |
| 独立 GQA 推理任务        | 原配置   | 原配置   | 不受影响              |

所有引用该字段的旧结果先标为 `needs_refresh`，再重新生成。没有重新执行的题目不能继续显示“当前完整回答”。字段依赖不清楚时，保守失效同对象相关结果，但不能失效整个会话的其他对象。

对象标识由程序核验。相同名称不能证明对象相同；一个输入中出现两个训练配置，应分别编号。相互冲突且没有明确更正顺序的条件应澄清，不能一律“最后一句覆盖”。

具体计算应使用受控公式、显式单位和确定性算术。LLM 负责解释和选择受支持公式，程序校验公式适用条件与输入后计算；不执行任意模型生成的代码或 `eval`。`GiB` 使用 `2^30` 字节，约定最终显示舍入，不把静态账本当实际峰值。此前 `14.668330550…` 的两位小数必须是 `14.67`，相关性门控不能替代此检查。

## 6. 长期存储与 JSON 契约

### 6.1 新会话建立什么

建议一个 PostgreSQL 应用库保存所有会话，每个新会话新建独立逻辑空间与 UUID。每个会话绑定一个现有知识库 UUID 和存储指纹。它不复制 TXT、分块或向量，也不执行 `CREATE DATABASE`。

物理上每会话一个数据库虽能实现，但会增加建库权限、连接管理、迁移、备份和清理成本，不能解决问题理解错误。只有确有独立备份、法律隔离或租户边界需求时再评估物理拆库。

长期上下文只保存子题及其必要支撑数据：任务目标、条件、引用、修订和状态。会话身份、轮次及请求执行元数据是隔离与恢复所需，并不是聊天全文。共用对象条件只服务于关联子题，不保存无关闲聊或任意会话摘要。

建议的关系设计如下，表名属于拟定：

| 表                       | 保存内容                               | 关键约束                                             |
| ----------------------- | ---------------------------------- | ------------------------------------------------ |
| `conversation_sessions` | 名称、知识库绑定、当前 revision、创建及归档状态       | 名称仅展示，UUID 是身份                                   |
| `question_versions`     | 稳定题号各版本的目标、来源片段、条件引用、状态及证据引用 JSONB | `(session_id, question_id, version)` 唯一；旧版本不可覆盖  |
| `object_versions`       | 子题共用对象的有效条件及来源                     | 对象与子题同会话；只有被子题引用的对象才持久化                          |
| `turn_requests`         | 请求摘要哈希、轮次、执行状态、受影响题目版本、usage 等元数据  | `(session_id, request_id)` 唯一；不默认保存原始消息全文或最终回答正文 |

当前题目列表可由每个稳定题号的最新版本生成；有实际查询性能需要再增加投影，不先引入独立历史向量库。归档、删除会话只作用于其上下文数据，不删除绑定的知识库。

```json
}
```

示例哈希和 ID 是占位值。精度名称与字节数之间的转换必须由字段类型规则验证；程序不能仅因为引用片段包含某些字词就接受任意新数值，也不能只看到“4 字节”就无条件推断为 FP32。示例的 `replace` 表示本次更正，具体字段操作由 `condition_changes` 限定。

`answer_refs` 保存依据引用，不能称为答案本身；一个节点可能只支持公式，具体结果还依赖用户条件和计算。长期保存的必要计算记录可包含公式标识、输入、单位、结果及舍入规则，并附属于该子题，不保存模型推理文本。

`answer_refs = null` 表示该版本没有已接纳的证据引用，具体原因由状态区分。不能让 `null` 同时无区分地表示“尚未检索”“无依据”和“检索异常”。

### 6.3 状态与更新规则

| 业务状态            | 含义               | 用户显示      |
| --------------- | ---------------- | --------- |
| `ready`         | 题意足够，尚待执行        | 待处理       |
| `waiting_input` | 缺少用户必须提供的对象或条件   | 聚焦补充问题    |
| `answered`      | 当前版本全部必要要求通过检查   | 本次答案      |
| `partial`       | 部分要求已回答，部分明确缺失   | 已答部分及未答范围 |
| `no_evidence`   | 本次检索未找到足够依据      | 该项“无”     |
| `needs_refresh` | 条件或知识来源变化，使旧验证失效 | 需重新验证     |
| `cancelled`     | 用户取消该题           | 已取消       |

执行状态另用 `queued/running/succeeded/failed/unknown`，不把 API 超时变成 `no_evidence`。`answered` 由生成、覆盖检查、引用检查和逐题门控共同确定，不由 LLM 在规划 JSON 中自行填写。

更新采用“追加子题版本 + 更新当前视图”。新目标使用新题号；旧题追问沿用稳定题号并增加版本。被取消或合并的编号不重新分配，合并关系保留，避免“第二题”随排序变化而指向别的内容。

### 6.4 不保存答案正文的代价

严格按照只存引用实现时，可以重建当前有效问题，重新读取仍有效的节点并再次生成；这不保证生成与上次逐字一致。

以下能力不能无条件承诺：精确修改“刚才答案第二点”、不增加事实的逐字格式转换、事后完整审计已展示答案、服务重启后原样重放已完成响应。答案哈希无法还原答案。

一期建议按用户要求保持引用模式。涉及旧回答具体措辞时，请用户提供那一段，或者明确提示将按原题和证据重新生成。若将来需要精确编辑，可另行选择“每题仅保存最终可见答案”，无需保存完整聊天；此选项不默认开启。

同一 `request_id` 的重放不得偷偷重新生成。进程内仍有结果时可重放；结果不再可用时返回已完成状态、题号与 `answer_not_retained`，需要一个明确的新生成请求才能再次调用模型。这是引用模式的接口约束。

## 7. 检索、低证据与回答合并

### 7.1 复用现有检索能力

每道可执行题使用精简的 `search_query`，保留主题、目标、版本及关键限制，不包含整段修订记录、来源审计字段和所有旧问题。生成使用完整有效条件，检索文本与生成输入不是同一份长字符串。

用于持久记录和跨进程缓存的语料版本必须来自可持久校验的文档版本清单或等价版本机制，不能只使用进程重启后可能重置的内存计数器。本次引用仍需核验实际文档与节点版本。

仍使用向量检索、BM25、RRF 和 CUDA Reranker。缓存键至少包含知识库身份、可持久校验的语料版本和规范检索输入；不同数据库或版本不能共用结果。

现有 V1.2 检索持有物理存储锁，因此不能只加异步并发就宣称多个子题并行加速。一期保留锁的正确性，先做等价请求去重和模型复用；有测量依据后再评估批处理。GPU Reranker 设置受控队列，避免多个子题抢显存。

证据按数据库、文档版本和节点身份去重；每题保留自己的 `allowed_evidence_ids`。相同节点服务多题时只在本轮证据池中保留一次，但不因此允许所有题引用全部节点。

### 7.2 “召回率低”的可执行定义

真正的召回率需要已知标准答案或全部相关节点，在线单次请求通常没有这个分母。RRF 分数、向量距离和 Reranker 分数也不是天然可互换的正确率。

本方案把需求实现为“严格证据不足策略”：一次完整混合检索和重排后，按照冻结阈值、对象与版本匹配、必要事实覆盖判断是否足够；不足的子题输出“无”，不自动靠模型常识补答，不默认无限扩检。

阈值通过有答案、无答案、相似但不同对象、不同版本的冻结样本校准；报告误拒有答案题和误放无答案题两种错误。默认不增加第二次搜索，诊断模式可单独对照“补检一次”的收益，但不能暗中改变生产策略。

“缺少用户输入”和“知识库缺资料”必须区分。GQA 数值题未给层数属于 `waiting_input`；用户明确询问某产品的保留期，而资料没有该事实，属于 `no_evidence`，不应反过来要求用户把答案告诉系统。服务不可达属于执行失败。

### 7.3 生成和门控

生成输入按题包含有效问题、条件、必要要求及允许的证据。输出应为 `items`，每项明确绑定 `question_id/version`。程序检查漏题、重复、越权引用、条件冲突及截断，门控逐题检查相关性与依据充分性。

部分题失败只影响对应题；其他已通过题正常输出。对于误拒、非法引用或非法结构，可配置每轮最多一次有界修复，修复只使用该题原有许可依据；技术错误不能自动改写成“无”。

最终以程序按用户目标顺序合并各题已通过的答案、澄清与状态。通常无需额外总结调用；跨题比较是明确目标时才作为依赖任务处理，并保持事实到原证据的可追溯关系，不能把未经验证的子题答案当新证据。

输出前复验文档和条件版本。节点 ID 与内容哈希可以发现失效，不能恢复已删除正文；失效时重新取证或标记 `needs_refresh`，不继续引用旧内容。

## 8. 上下文与调用容量

### 8.1 持久化 JSON 不直接作为 Prompt

应分开维护四种表示：长期记录、历史候选目录、生成输入、门控输入。

| 表示   | 包含                          | 不包含                |
| ---- | --------------------------- | ------------------ |
| 长期记录 | 稳定身份、修订、原文片段、条件来源、状态、引用     | 无关闲聊和默认保存的完整生成正文   |
| 规划输入 | 当前消息、少量相关题目目录、有效对象摘要、历史覆盖说明 | 全会话全部版本            |
| 生成输入 | 当前有效目标、条件值与单位、输出要求、去重证据正文   | 每个字段重复的完整来源、所有旧题全文 |
| 门控输入 | 该批题目要求、有效条件、候选答案及对应证据       | 无关子题、原始推理内容        |

必须先定位必要历史，再安排 Token。不能先截取最近几轮，然后把截掉的任务当成不存在。超长文档依据按完整事实单元选择，不从中间截断到改变含义。

### 8.2 容量规则

每个阶段独立检查：

```text
actual_input_tokens + reserved_output_tokens + safety_margin <= provider_context_limit
reserved_output_tokens <= min(provider_output_limit, application_stage_limit)
thinking_tokens + body_tokens <= shared_output_limit  # 当供应商采用共享输出额度时
```

输入统计包括 system/user 消息、JSON Schema、工具定义（如实际启用）、证据、必要历史及格式开销。无法精确使用供应商 tokenizer 时标明估算口径，保留余量，并用真实 usage 校准。

V1.2 在模型适配器里声明的 `context_window=1_000_000` 只是客户端配置，不能独立证明当前服务、模型和调用方式允许使用这一容量。开发时须核对实际模型规格，并测试最终 HTTP 参数；历史上已有调用级 `max_tokens` 被实例值覆盖的问题。

生成前同时预估下游门控需要装入的候选答案，必要时按题分批。超过容量时先减少可选细节和无关证据，再受控分批；单题仍放不下时明确报告容量问题。不能静默漏题、随意截掉条件，或用“无依据”掩盖容量不足。

每题最低输出要求与整轮任务数量必须检查。任务上限及分批规模作为可配置的运行限制，在基准后冻结；超限要明确列出未执行目标，不能只处理前若干题却声称全部完成。

本方案不设金额上限，但仍需单次超时、有限修复与重试、输出长度限制。金额、上下文容量、阶段输出上限和超时是不同概念。预算账本区分预留、真实 usage 和未知消耗，不能把每次最大预留永久累加，也不能把缺失 usage 计零。

## 9. 深度思考与流式接收

### 9.1 建议默认关闭，按阶段选择

| 阶段        | 一期建议                   | 原因及必要校验                          |
| --------- | ---------------------- | -------------------------------- |
| 问题分解与操作抽取 | 显式关闭思考                 | 目标是稳定短 JSON；仍需 Schema、覆盖、等价及来源检查 |
| 历史定位      | 程序精确读取，必要时让 API 判断有限候选 | 不让模型凭思考生成历史身份                    |
| 条件合并      | 程序为主                   | 已验证的字段操作不需要自由生成推理                |
| 普通知识问答    | 默认关闭                   | 先验证不依赖深度思考的稳定基线                  |
| 复杂推导和比较   | 可配置开启，先小规模对照           | 思考可能改善质量，也会增加延迟和输出占用，不能保证收益      |
| 逐题门控      | 默认关闭，返回短结构化判断          | 校验仍依赖证据和规则；计算单独检查                |

2026-10-21 核对的 DeepSeek 官方文档说明思考模式默认开启，可显式发送 `thinking.type=disabled`。因此“代码没有写开启”不等于关闭；验收必须检查实际请求。

开启思考与流式传输是两个独立选项。流式能够分段接收，但不会扩容上下文，也不会阻止推理消耗正文额度。即使关闭思考，也必须做去重与覆盖检查；这些校验不能用深度思考代替。

### 9.2 中间 JSON 的推荐替代

推荐每次 API 调用创建一个请求内存对象，而不是所有会话共享一个磁盘 JSON。这里的“每次”指每次规划、生成、门控或修复调用，不只是每轮用户消息。

```json
{
  "request_id": "request_example",
  "call_id": "call_example",
  "stage": "generation",
  "attempt": 1,
  "state": "receiving",
  "reasoning_content": null,
  "content": "",
  "finish_reason": null,
  "usage": null
}
```

`reasoning_content` 与 `content` 分开处理，只将完整 `content` 交给后续业务解析。默认不长期保存供应商返回的原始推理；可记录推理 Token 用量、首正文到达时间等指标。需要诊断时再受限保存，不把它当证据或作为下一轮事实。

接收规则如下：

1. 新建缓冲时置空正文并绑定 `request_id/call_id/stage/attempt`，不能沿用上一次内容。
2. 分别检查一个分片的推理增量与正文增量；不能假定二者永远互斥，也不能遇到空字段就退出。
3. 正确处理没有 `choices`、只有 usage 的尾帧及空增量。
4. 接收完成后检查终止原因、正文非空、JSON 完整、Schema、题号集合及语义规则。
5. 截断、断流或非法 JSON 不能进入已完成状态；有限重试采用新缓冲，不把两个 attempt 拼接。
6. 限制缓冲大小与接收时间，避免无限累积。取消连接不等于供应商一定停止计算或计费。
7. 原始正文未门控前，只显示阶段进度，不作为正式答案逐字发布；通过检查后再输出已验证内容。

单文件适合串行 CLI 的“最近一次诊断快照”，不适合服务端消息队列。若保留固定文件，建议采用进程互斥、内存接收完成后原子替换，短暂临时文件用于防止写坏；长期只保留一个最新快照。若要求连临时文件都不能存在，就无法同时承诺普通文件更新的崩溃原子性，应该改用内存对象或数据库事务。

一期结构化文本调用建议不使用供应商工具调用协议。当前 DeepSeek 文档规定，不带 `tools` 时无需回传 `reasoning_content`；带 `tools` 的思考调用有不同的回传要求。未来启用工具调用必须另做适配，不能套用本段的丢弃规则。

JSON Output 只保证格式方向，不能保证字段正确或内容非空。官方文档仍提示空内容和截断风险，因此必须保留应用层校验。

## 10. 一致性、失败与存储负担

同会话请求按顺序处理，通过 `expected_revision` 防止两个请求覆盖同一版本。数据库短事务只承担请求认领和结果提交，不跨检索、模型调用或长时间流式接收持有事务。

同一 `request_id`、相同请求摘要返回已知执行状态；相同 ID 配不同内容返回冲突。提交前确定失败可释放认领并记录原因；结果确实未知时保留恢复状态，不能盲目重发付费调用。HTTP 超时或用户断开不能自动证明远端没有执行。

对象版本、受影响子题版本和会话 revision 在同一提交中更新。对于有效的用户条件补充，即使后续模型失败，也可在受控提交中保留已验证的新条件，并将关联任务标为待执行或需刷新；不得写入未通过的模型候选答案。应在实现前冻结此恢复语义并测试，不能异常时随意丢掉已确认输入。

历史候选索引为派生数据，可由子题记录重建；增加该索引时，同事务写入待更新标记，后台幂等补齐。索引更新失败不重新触发已完成生成。

长期存储的主要新增量来自子题版本、条件来源和引用映射，不为每题复制知识向量。历史版本会增长，应按实际新增字节测量；不能宣称“只存引用所以没有存储开销”。删除历史版本也会削弱旧版本追问能力，清理必须有明确保留策略。

应用和 LlamaIndex 日志统一进入 `logs/`，默认仅记录阶段、状态、耗时、大小和摘要，不把完整 Prompt、所有节点正文、原始推理或凭据永久写入常规日志。诊断导出应显式开启并设置保留期限，避免通过日志绕过“只保留子题上下文”的约定。

PostgreSQL 的并发能力不能消除当前 Qdrant/JSON docstore 组合的物理锁限制。本方案一期按当前单持有者方式运行，不宣称已经支持多个服务实例共同读写同库。

## 11. CLI 与 API 接口拟定

以下命令是建议接口，V1.2 尚不支持新增的 `conversation`、`question`、`ask` 等命令，本轮没有运行它们。

### 11.1 命令行会话

```text
uv run story-rag shell
story-rag> db use "牛客面试"
story-rag[牛客面试]> conversation create "训练与推理排查"
story-rag[牛客面试|训练与推理排查|r0]> ask "分别说明 ZeRO-2 和 ZeRO-3 的分片规则；另一个 GQA 服务的 KV 占用需要哪些配置？"
story-rag[牛客面试|训练与推理排查|r1]> question list
story-rag[牛客面试|训练与推理排查|r1]> question show Q002
story-rag[牛客面试|训练与推理排查|r1]> ask "那套服务有32层，每层8个KV头……" --question Q002
story-rag[牛客面试|训练与推理排查|r2]> question history Q002
story-rag[牛客面试|训练与推理排查|r2]> conversation list
story-rag[牛客面试|训练与推理排查|r2]> conversation use <session-id>
```

`conversation create` 创建并选择新会话，长期保存；重启 CLI 后通过 `conversation list/use` 恢复。选择后在提示符显示库名、会话名和 revision。会话列表展示 ID、名称、绑定库、子题数量、待补数量及更新时间。

| 命令                                                  | 行为                                 |
| --------------------------------------------------- | ---------------------------------- |
| `query "问题"`                                        | 保留现有零生成调用的单轮检索预览，不写会话              |
| `ask "消息"`                                          | 在选定会话中规划、检索、生成和更新题目                |
| `ask "消息" --question Q002`                          | 显式指定默认关联题；子任务自己的明确引用仍须独立验证         |
| `ask "消息" --no-history`                             | 禁止历史定位和历史条件继承；只按本轮自足信息执行，不能同时传历史题号 |
| `question list/show/history`                        | 查看稳定题号、当前状态、版本、条件和证据引用             |
| `question cancel Q002`                              | 标记取消，不删除知识来源或复用题号                  |
| `conversation archive <id>`                         | 归档会话并解除选择，可继续保留历史                  |
| `conversation delete <id> --dry-run`                | 展示删除范围及确认身份                        |
| `conversation delete <id> --confirm-id <id>`        | 删除该会话关联上下文，知识库保持独立                 |
| `conversation diagnose --plan-file <path> --no-llm` | 注入已冻结计划或 Mock，导出解析后链路，不调用远程模型，不提交  |
| `conversation diagnose --message "..." --live-plan` | 显式进行真实规划诊断；需要模型调用，结果仍不提交业务状态       |

切换知识库时解除当前会话选择，不能把原会话悄悄绑定到新库。选择会话时核对当前库身份，身份不一致返回提示；同名库删除重建后不得继承旧会话绑定。

`--no-history` 的首版语义为在同一会话中创建不依赖旧记录的新任务；仍进行必要身份、幂等和 revision 校验。这些控制元数据读取不等于读取历史内容。输出语言等偏好也不能从旧题暗中继承。

### 11.2 生产与诊断端口

模块“端口”指明确的 Python 接口与 HTTP 接口，不要求每个模块另开一个 TCP 服务。

| 模块   | 生产接口                                        | 诊断接口及导出                                   |
| ---- | ------------------------------------------- | ----------------------------------------- |
| 会话存储 | `create_session/get_session/commit_request` | `inspect_scope/inspect_versions`，限定隔离测试数据 |

| 历史定位 | `resolve_history`                           | `history_trace`，输出候选、选中依据及拒绝原因            |
| 条件更新 | `apply_changes`                             | `condition_diff`，输出字段级前后值和影响题号            |
| 分题检索 | `retrieve_tasks`                            | `retrieval_trace`，输出各阶段节点、排名与耗时           |
| 输入组装 | `prepare_generation`                        | `preview_messages`，导出最终 messages、计数及分批计划  |
| 回答验证 | `validate_items`                            | `validation_trace`，注入候选及门控结果，输出漏题、引用和数值检查 |
| 编排   | `answer_turn`                               | `run_diagnostic`，不提交业务状态，区分 Mock 与真实调用    |

拟定 HTTP 接口：

```text
POST   /v1/conversations
GET    /v1/conversations
GET    /v1/conversations/{session_id}/questions
GET    /v1/conversations/{session_id}/questions/{question_id}/versions
POST   /v1/conversations/{session_id}/turns
POST   /v1/conversations/{session_id}/archive
DELETE /v1/conversations/{session_id}
POST   /debug/conversations/{session_id}/preview
```

轮次请求包含 `request_id/expected_revision/message/reply_to/use_history`；服务器根据会话确定知识库，模型不能选库。返回 `request_id/revision/status/items/answer/metrics`，每项包含稳定题号、版本、状态、引用和本次显示内容。

返回中的 `answer` 只存在于响应和必要的短期内存中，按引用模式不默认长期入库。重放接口明确使用 `answer_not_retained`，不能把无正文误报为业务“无答案”。

诊断接口默认关闭或限制本地开发访问，不把生产凭据和完整数据库账本暴露出去。远程部署鉴权和多租户隔离需要独立验收。

## 12. LlamaIndex 选型与影响文件

### 12.1 原生优先，不让原生组件承担不适合的职责

| 能力    | 已核对的 LlamaIndex 能力                                  | 采用方式                                        |

| L05 | 3      | 缺参、澄清、短答补充         | waiting_input 能转为可执行，不能无限澄清 |

| 合计  | 38     | 12 组               | 用户请求数与模型调用数分开统计             |

深度思考是否值得开启，另做可选固定输入对照：选 6 个有代表性的复杂生成输入，开/关各重复 2 次，共 24 次生成调用；固定证据、条件和正文验收标准，不重新跑整条检索链。记录正确率、遗漏率、结构合法率、正文长度、推理与正文 Token、首正文时间和总耗时。此对照不包含在 38 个请求位置中，也不属于本次文档保存已执行的操作。

### 13.15 指标与通过标准

| 类别    | 指标或断言                                               |
| ----- | --------------------------------------------------- |
| 任务理解  | 原目标覆盖率、重复执行率、误合并率；分别统计而非只看子题数量                      |
| 历史定位  | 显式引用命中、窗口外命中、歧义正确澄清、跨会话与跨库拒绝                        |
| 条件    | 字段值、单位、来源、对象范围、更正链和受影响题目集合                          |
| 检索    | 有参考节点时报告 Hit@K/MRR/Recall@K；无标准答案时报告证据接受与拒绝，不伪称召回率  |
| 输出    | 逐题必要要求覆盖、引用合法、事实依据、数值正确、部分成功保留                      |
| 状态    | waiting_input 恢复、needs_refresh 传播、失败释放、revision 与幂等 |
| 时间    | 规划、定位、检索、重排、组装、生成、门控、提交；嵌套计时不直接相加                   |
| 资源    | Python RSS/Private Bytes、GPU 显存、各相关服务口径；记录采样间隔和缺测   |
| 调用与容量 | 实际请求参数、输入/输出/推理用量、估算误差、调用与修复次数、unknown usage        |
| 存储    | 每轮及每子题新增字节、历史版本数量、日志增长、正文或向量重复量                     |

确定性契约与隔离断言必须全部通过。真实语义测试不得出现跨会话读取、静默漏目标、未经说明的错误合并、已确认条件串用或错误引用；质量失败逐项保留，不用整体平均分掩盖。

评估使用 `BatchEvalRunner` 配合 `ContextRelevancyEvaluator`、`CorrectnessEvaluator`、`RelevancyEvaluator`、`FaithfulnessEvaluator`。评分针对本批已经生成并保存到测试报告的输出，不为了评分再次生成答案；测试报告是显式诊断产物，与生产不留正文的策略区分。

`DatasetGenerator` 可辅助生成候选题，当前已安装版本有弃用标记，不能把候选自动当 gold。正式题目、参考事实、对象关系和无答案标签需人工核验冻结。任务身份、条件、公式和执行状态主要用程序断言，不依赖 LLM 评分替代。

## 15. 建议敲定的默认行为

1. 新对话创建 PostgreSQL 逻辑会话，固定绑定已有知识库身份。
2. 长期只保存子题、关联对象条件、必要来源片段、证据引用、版本和执行元数据。

6. 后续问题按明确关系更新当前题目视图，旧版本保留；条件修改统一作用于关联对象。
7. 默认单次完整混合检索，证据不足则该项“无”，内部不将其夸大为已证明全库无答案。
8. 规划与门控显式关闭深度思考，复杂生成是否开启由固定输入对照决定。

### 17.1 B07：语言偏好与作用范围

语言偏好与问题内容分开存储，并明确作用范围。语言偏好可以保存在会话或子题的 JSONB 记录中，但不能只保存一个没有作用域的 `language` 字段，否则无法区分“本题使用英文”“本轮所有题使用英文”和“后续会话默认使用英文”。

建议结构如下：

```json
{
  "language_preferences": {
    "conversation_default": {
      "language": "zh-CN",
      "source_turn_id": "turn_12",
      "source_quote": "之后的回答都用中文",
      "supersedes": "pref_03"
    },
    "turn_override": {
      "language": "en",
      "source_turn_id": "turn_14",
      "source_quote": "下面几个问题都用英文回答"
    },
    "question_overrides": {
      "Q002": {
        "language": "en",
        "source_turn_id": "turn_14",
        "source_quote": "这题请用英文回答"
      }
    }
  }
}
```

解析用户消息时，需要区分“问题使用什么语言”和“回答偏好是什么语言”：

| 用户表达           | 处理方式                  |
| -------------- | --------------------- |
| “这题请用英文回答”     | 只作用于明确指向的子题           |
| “下面几个问题都用英文回答” | 作用于本轮明确覆盖的所有子题        |
| “以后都用英文回答”     | 更新会话长期默认偏好            |
| “用英文介绍 AOF”    | 作为当前任务的输出要求，不自动改写长期偏好 |
| 用户使用英文提问       | 不单独视为要求英文回答           |

LLM 可以提出语言和作用范围候选，但必须返回当前用户消息中的原文片段。程序需要校验原文片段确实存在，并核对其作用范围、指向题目和变更关系。不能由模型凭空声明长期偏好，也不能从旧问题或旧答案默默推断偏好。

语言偏好的优先级固定为：

1. 当前子题的明确语言要求；
2. 当前轮次的明确语言要求；
3. 会话长期默认偏好；
4. 系统默认语言。

如果当前消息明确改变语言偏好，应追加新的偏好记录并通过 `supersedes` 或版本关系替换当前视图，旧偏好仍保留。某一题的语言要求不能污染同轮其他题；新话题也不能自动继承只属于旧题的语言覆盖。

B07 的回归必须同时检查语言内容和作用范围：当前题要求英文时该题使用英文；同轮未指定的题仍按本轮或会话默认处理；“以后都用英文”在后续轮次生效；普通英文提问不能单独触发永久英文偏好。

### 17.2 B12：语义重复拆题与任务关系判断

B12 不能简单通过减少子问题数量解决。核心规则是先保留用户的全部原始目标，再判断目标之间的关系；任何去重都必须留下“原始目标 -> 执行任务 -> 输出要求”的映射。

每个候选目标至少拆出以下字段：对象、所求目标、条件、版本或时间范围、答案维度、依赖关系和输出要求。LLM 可以提出关系候选，程序负责确认关系、检查目标覆盖和决定是否允许合并。

| 关系类型                      | 示例                             | 处理                         |
| ------------------------- | ------------------------------ | -------------------------- |
| `duplicate` 重复目标          | “AOF 的缺点”和“AOF 的不足”，对象、条件和版本一致 | 合并为一次执行；保留两个原始目标到同一执行任务的映射 |
| `requirements` 同一目标的多个要求  | “给出公式、分项、总计，并用表格”              | 作为一题的多个输出要求，不拆成多次计算        |
| `shared_context` 不同目标共享条件 | “解释分片规则，再计算每卡显存”               | 保留两个目标，可共享对象条件和部分证据        |
| `compare` 比较分支            | “分别计算 BF16 与 FP32”             | 保留两个条件分支，不能按相似度合并          |
| `dependency` 真实依赖         | “先算总量，再判断是否超过预算”               | 建立先后关系，后者依赖前者的已验证结果        |
| `ambiguous` 不确定关系         | 仅因措辞相似但目标或范围不清楚                | 暂不合并，必要时请求澄清               |

判断任务是否本质相同时，至少比较对象、所求目标、适用条件、版本或时间、答案维度、范围和依赖。句子相似度、Embedding 或 Reranker 只能用于找候选，不能单独证明两个问题等价。跨语言同义目标必须先确认对象、条件和输出维度一致后才可合并。

去重后必须检查：

- 每个原始目标都有一个或多个执行任务映射；
- 合并任务保留所有原始输出要求；
- 优点和缺点、原理和计算、当前方案和比较方案等不同维度没有被误合并；
- 比较分支的条件、答案和证据关系保持独立；
- 同一公式、同一对象版本和同一输入条件可以复用确定性计算结果，避免重复计算；
- 任何不确定的候选关系都不能为了减少任务数而强制合并。

B12 的指标不只统计子问题数量，还要统计原始目标覆盖率、误合并数、重复执行数、被遗漏的输出要求和真实依赖是否保持。

### 17.3 B13：历史条件来源与当前来源的区分

B13 不能依靠 LLM 自己生成的 `quote` 作为可信来源。条件值应采用类型化结构，记录值、单位、对象、字段、操作和来源：

```json
{
  "object_id": "train_a",
  "field": "gradient_dtype",
  "value": "FP32",
  "unit": null,
  "provenance": {
    "kind": "user_explicit",
    "source_turn_id": "turn_08",
    "source_quote": "梯度实际采用 FP32 累积"
  }
}
```

来源类型至少包括：

| 来源类型            | 含义                     |
| --------------- | ---------------------- |
| `user_explicit` | 用户在当前或指定历史轮次明确提供的值     |
| `inherited`     | 从已核验的历史条件继承，必须保留原始来源   |
| `derived`       | 根据受控公式、已验证输入和单位确定性计算得到 |
| `retrieved`     | 从带版本的知识节点中读取           |

用户说“其他条件保持不变”时，程序应继承既有值及其原来源，不能把这句话当作新数值的来源。当前消息的 quote 即使存在，也必须验证它是否同时支持对应字段、操作和值。“参数量保持不变”不能为此前没有出现的参数量提供新数值来源。

来源校验至少包括：

1. `source_turn_id` 属于当前会话且未超过允许的 `as_of_revision`；
2. 引用片段确实来自对应轮次或对应的用户材料；
3. 引用片段支持该字段和操作，而不是只包含相关关键词；
4. 继承值继续指向原始来源，不被模型伪装成当前用户新提供的值；
5. 数值、单位、精度和对象字段通过类型化校验；
6. 派生值记录公式版本、输入、单位、舍入规则和依赖来源。

无法确认语义来源时，条件不得进入有效版本，应标为缺失、待澄清或技术失败。字面上包含字段名的 quote 不能单独证明数值来源正确。B13 与 B24 联动：LLM 可以解释公式和选择任务，但数值计算、单位换算和舍入必须由确定性计算逻辑复核。

### 17.4 B19：最终发送参数检查不单独增加用户场景编号

B19 可以不新增独立的用户场景编号。用例编号的作用是追踪和统计，不是每个底层契约都必须占用一个自然语言场景。B19 应作为模型调用与容量契约测试的一部分，以参数化方式覆盖规划、生成、门控和局部修复阶段。

测试不能只断言 Python 函数收到的 `max_tokens` 参数，而必须通过 HTTP Mock 或请求拦截器检查最终序列化的 HTTP 请求体，确认每个阶段实际发送的输出上限、思考模式、模型名和必要的上下文参数均符合阶段配置。这样既覆盖 B19，也能同时覆盖 B18 的思考模式设置和容量计算，不需要额外编造一轮业务对话。

方案中的测试矩阵应将 B19 标记为“模型发送层契约测试”，并记录：规划阶段上限、生成阶段上限、门控阶段上限、修复阶段上限、实际请求体值和断言结果。若底层适配器再次用实例级默认值覆盖调用级值，测试必须直接失败。

### 17.5 B23：逐题、分层的门控设计

B23 的门控由程序确定性检查和逐题结构化语义审核共同组成。不能把“相关性、证据充分性、任务覆盖、引用权限和提示注入判断”压缩为一个整体 `Yes/No`。

#### 17.5.1 第一层：程序确定性检查

每个生成项必须通过以下检查：

- `question_id`、版本和原始目标映射存在且唯一；
- 没有遗漏必要目标，也没有重复回答同一目标；
- 引用节点属于该题的 `allowed_evidence_ids`；
- 文档、节点和语料版本仍然有效；
- 题目要求的对象、条件、版本、单位、范围和否定约束没有冲突；
- 输出语言符合当前题目的有效语言偏好；
- 表格、列表、字数、格式和其他明确输出要求已满足；
- 公式、单位换算、数值和舍入通过确定性校验；
- 响应正文完整，不能是空正文、截断 JSON 或混入未允许的结构。

程序检查失败时，应返回字段级原因。技术结构错误、证据越权、失效来源和数值错误不能直接转换成“无依据”。

#### 17.5.2 第二层：逐题结构化语义审核

对每个题目独立判断：

```json
{
  "question_id": "Q002",
  "scope_ok": true,
  "requirements_covered": ["分片规则", "每卡显存"],
  "requirements_missing": [],
  "evidence_supported": true,
  "answer_relevant": true,
  "unsupported_claims": [],
  "prompt_injection_detected_in_evidence": false,
  "decision": "accept"
}
```

语义审核只能使用该题的有效目标、条件和允许证据。引用节点中的“忽略规则”或其他指令性文本必须作为不可信内容处理，不能改变会话、数据库或证据权限；同时，出现这类文本不能自动导致该题的合法事实回答被整体误拒。

#### 17.5.3 第三层：按题处置与有限修复

逐题结果按以下规则处理：

| 情况                 | 处理                                  |
| ------------------ | ----------------------------------- |
| 完整通过               | 输出该题答案并写入有效历史                       |
| 有依据但部分要求缺失         | 保留已支持部分，明确未覆盖范围，状态为 `partial`       |
| 知识库缺少该事实           | 该题状态为 `no_evidence`，输出“无”，不要求用户提供答案 |
| 缺少用户必须提供的参数        | 状态为 `waiting_input`，提出聚焦补充问题        |
| 引用越权、结构错误或可定位的覆盖错误 | 最多进行一次局部修复，只使用该题原有允许证据，然后重新执行全部检查   |
| 技术失败、结果未知或门控无法完成   | 保留明确失败状态，不伪装为“无依据”，不写入有效答案          |

一题被拒绝不能抹掉同轮其他已通过的题。跨题合并输出由程序按照原始目标顺序完成；未经验证的子题答案不能变成另一题的证据。

#### 17.5.4 B23 必须加入的回归样例

需要保留历史失败样例并逐题验证：

- MT15：有依据的 Python 缓解回答不能被整体门控拒绝；
- MT31：有依据的“7 天”回答不能被门控拒绝；
- MT36/U1：引用对象包含角色 JSON 或指令性文本时，合法的 AOF 问题仍应按证据判断；
- 证据确实不支持的具体事实必须拒绝或标记 `no_evidence`；
- 一题有依据、一题无依据时，前者保留，后者单独输出“无”；
- 引用中的提示注入不能改变系统范围，也不能让正常事实问题被无差别拒绝。

报告必须分别统计误拒和误放，不能只给总体通过率。LlamaIndex 的 Faithfulness、Context Relevancy、Correctness 和 Relevancy Evaluator 可用于回答质量评估，但不能替代题号、覆盖、证据权限、条件版本和数值的程序断言。

### 17.6 B25-B26：失败时恢复到最近一次已提交状态

“自动回到上一次对话”可行，但语义应限定为：**丢弃本次请求尚未提交的候选状态，保留此前已经成功提交的会话版本。** 不能删除或回退已经有效的历史轮次，也不能撤销远端 LLM 已经发生的调用或费用。

建议将每次请求建模为基于当前 revision 的临时尝试：

```text
当前已提交 revision N
  -> 请求基于 N 执行，候选任务、条件和答案暂存
  -> 正常回答、部分回答或待补状态：原子提交为 N+1
  -> 确定的提交前技术失败：丢弃候选改动，记录失败，继续使用 N
  -> 结果未知：保留 N，记录 unknown，不自动重发同一个付费 request_id
```

因此，原先为防止并发写入而设置的请求执行租约不能表现为永久锁死对话。租约只在请求处理期间保护同一 `expected_revision`，确定失败时立即释放，并设置过期恢复和 fencing 校验，防止过期任务迟到后覆盖新 revision。

以下状态应提交：正常回答、部分成功、`waiting_input`、明确的 `no_evidence` 和用户主动取消后的已确认业务结果。以下情况应回滚本轮候选状态：非法规划、非法 JSON、证据越权、门控无法完成、确定的容量失败、确定的本地技术失败。服务异常、远端超时、客户端断开和提交确认不明属于 `unknown`，不能假定远端没有执行。

方案原先提出“即使后续模型失败，也可以保存已验证的新条件”。这与完整的失败回滚语义冲突，现修订为：失败时将该条件保留为未生效草稿或失败诊断记录；只有用户补交或新的请求成功完成后，条件才进入有效版本。这样失败轮次不会污染后续题目。

远端调用已经发生时，本地回滚只能恢复会话账本，不能保证供应商停止计算或撤销计费。相同 `request_id` 重试应先返回已知失败或 `unknown` 状态；只有显式发起新的请求 ID，且经过明确的恢复策略，才能再次调用模型。迟到结果必须校验原 revision 和 fencing token，不能写入已变化的会话。

该设计影响会话账本、请求状态、工作流收尾、CLI/API 状态展示和历史派生索引更新，不影响知识库中的 Qdrant、JSON Docstore、TXT 和现有物理存储锁。索引更新失败时通过 outbox 幂等补偿，不撤销已经提交的业务答案；对话请求租约和知识库物理写锁必须保持为两个独立机制。

### 17.7 P01 暂不处理

P01 的分题检索延迟暂时不进入本轮实现范围，不进行并发检索、Reranker 队列或查询缓存优化。现阶段仍保留各阶段耗时、查询长度、重复检索次数和 Reranker 耗时记录，后续可据实测数据单独设计性能方案。P01 不得被标记为已解决，也不能用功能测试通过替代性能验收。

### 17.8 本节对默认行为的修订

本节新增或修订以下默认行为：

1. 语言偏好按会话、本轮和子题分别保存，当前明确要求优先于长期默认偏好；
2. 用户原始目标全部保留，重复目标才允许合并，比较、互补和依赖目标不得误合并；
3. 历史继承值保留原来源，当前轮次的“保持不变”不能伪造新来源；
4. B19 作为最终 HTTP 发送层契约测试覆盖，不强制新增独立用户场景编号；
5. 门控逐题执行，程序断言优先，语义审核按题返回结构化结果，局部修复最多一次；
6. 确定技术失败自动丢弃本轮未提交状态，`unknown` 保留诊断并禁止静默重放；
7. P01 保留观测数据，暂不实施性能优化。
