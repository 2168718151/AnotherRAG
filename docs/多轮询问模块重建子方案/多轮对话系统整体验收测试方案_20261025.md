## 1. 验收目标与现状

目标是验证：**从会话请求到最终可见回复，任务是否完整、历史是否接对、知识证据是否匹配、禁止动作是否被挡住，失败后能否安全继续。** 不以 `pytest` 通过数或整轮 `succeeded` 状态代替逐题答案验收。

已有证据：方案零五轮使用隔离 PostgreSQL、固定 Mock 知识证据及真实 DeepSeek 规划/生成/门控，连续提交 revision 1→5；逐轮任务数为 3、2、2、1、2。最近记录为 303 passed、4 skipped；两项真实会话测试默认关闭，两项 LM Studio Embedding 不可达。**真实 Embedding→Qdrant→BM25/RRF→Reranker→生成的完整知识链尚未由这批五轮验证。** 第四轮曾出现建议“通知发起人”的违规回答；随后实际五轮输出已修正，但仍须专项证明“局部修复后若依旧违规，候选不得提交”。旧 MT15、MT31、MT36/U1 门控误拒仍待原语料复验。

原子方案的“唯一五轮对话”约束仍适用于**每个子方案完成后的快速回归**。本文件是整个系统的专项验收：除方案零外，采用原设计第 13.14 节的 12 组连续会话。测试库、测试会话和报告与主库分离。

## 2. 测试前冻结与 gold

1. 记录 Git SHA、Python/依赖锁、LLM 模型及实际 HTTP 请求体中的 `thinking`、`max_tokens`、上下文限制、Embedding/Reranker 版本与设备、Qdrant 集合 UUID/指纹、Docstore 与 TXT 源文件清单/哈希。知识快照与 PostgreSQL 测试 schema 一起标识；不同快照不可混算命中率。
2. 方案零五轮用户消息逐字取自[原文](00-唯一连续回归用例.md)，不得改写或把预期答案注入 Prompt。L01–L12 先冻结逐轮原文、知识可答性、候选来源及参考节点，再执行。人工 gold 逐题列出：原始目标及顺序、子题关系、预期历史 ID/对象版本、有效条件与禁止动作、允许证据、状态和必须/不得出现的事实。
3. 区分知识库节点、用户本轮事实、历史已验证业务状态、助手旧回复；后两者不能自动变成知识证据。第五轮工单日志只在该轮出现。每题标注 `answerable / missing_user_input / no_evidence / technical_unknown`。
4. 每个请求位置留存阶段输出、最终输入 messages、节点 ID/分数、生成与门控项、最终可见答案、revision、request ID、实际发送参数、finish reason、usage 与耗时。含 Prompt/正文的产物置于被 Git 忽略的受限 `reports/`；应用与 LlamaIndex 日志写入 `logs/`，不得记录凭据。
5. 同义表达按语义判分，如“排队”与“进入队列”均满足后台队列要求；区分“**不得通知**”和“**通知发起人**”。自动断言负责稳定身份、题数、状态、引用及关键否定约束，人工 gold 核验实际语义。

## 3. 分层执行顺序

| 关口 | 测试方式 | 必须验证 | 失败处理 |
| --- | --- | --- | --- |
| A 确定性契约 | 隔离 PostgreSQL、固定计划/证据、Mock 模型；方案零五轮及参数化故障 | 稳定 ID、题号/目标映射、来源/条件版本、会话与库隔离、预算、门控、提交/恢复 | 修复后重跑 A；Mock 成绩不等于真实模型质量 |
| B 固定证据真实 LLM | 方案零五轮，隔离账本及固定人工核验的知识证据；真实规划、生成、逐题门控 | 每轮 gold 与最终回复通过；完成禁止动作专项；记录真实请求与 Token | 保留失败原始响应，不靠新抽样覆盖失败 |
| C 真实知识全链 | 真实 TXT/Embedding、隔离 Qdrant+Docstore、BM25/RRF、本地 Reranker、真实 LLM、隔离账本 | 方案零及 L01–L12 穿过生产入口；逐题核验检索、输入和回复 | 归因为召回、重排、组装、生成或门控 |
| D 故障恢复 | 在规划、历史读取、检索、生成、门控、提交和索引更新边界注入错误 | revision、幂等、unknown、恢复和下一请求符合契约；违规候选不能提交 | 阻断整体验收，留故障时点和账本快照 |
| E 稳定性与资源 | 固定快照重复完整基准；测资源、延迟、日志及存储增长 | 关键硬门槛每次满足，报告 P50/P95 和波动；性能上限依据 C 基线再冻结 | 不挑最好的一次作为结论 |

各关口使用专用 schema/集合/目录及唯一运行 ID。运行前确认主 Qdrant 集合、主 PostgreSQL schema、旧报告和源 TXT 均不在写入目标；结束时保留隔离产物，不覆盖历史报告。

## 5. 必测缺陷与极端路径

| 工作流部位 | 注入或复现 | 必须观察到的结果 |
| --- | --- | --- |
| 生成后的禁止动作校验 | 方案零第四轮 Mock 生成“通知发起人” | 违规项被拦，不能进入可见回复或有效历史；“不得通知”不得误拒 |
| 局部修复 | 一次修复删掉通知建议，另一次修复仍坚持通知 | 前者复核后才提交；后者不得提交违规答案、revision 不增加，留下明确失败诊断且会话可恢复。无专项证据前属阻断项 |
| 任务覆盖和历史 | 缺子题、重复题号、同名对象、窗口外历史、关闭历史又带旧题 ID | 逐目标映射和唯一题号一致；歧义澄清；跨会话/库及 `--no-history` 冲突明确拒绝 |
| 证据与门控 | 一题有证据一题无；仅 Q001 可用节点被 Q002 引用；重放 MT15、MT31、MT36/U1 | 成功题保留、无依据题单独“无”；越权引用拒绝；分别统计误拒和误放 |
| 数值 | `15750000000 / 2^30` 及不同量纲/舍入边界 | 两位小数为 `14.67 GiB`；错误数值不能作为正确答案放行；未有通用校验器时据实标未通过 |
| 预算和发送 | 多题、长历史、JSON 转义扩张、门控含候选、usage 缺失或估算偏差 | 调用前预检生成和门控；分批或显式失败；检查真实 HTTP 阶段参数、finish reason/usage，未知不计零 |
| 结构和流式 | 非法 JSON、空正文、`length` 截断、reasoning/content 同帧、仅 usage 尾帧、断流与取消 | 有限修复、缓冲隔离和错误分型；残缺结果不写成 answered/no_evidence |
| 账本和恢复 | 同 ID 换内容、同 revision 并发、远端响应不明、提交后响应丢失、索引更新失败 | 冲突显式返回；确定失败释放；unknown 不重复付费生成；重放只返回能恢复的内容；索引补偿幂等 |
| 隔离和安全 | 引用 ID 或证据文本要求读别的会话/数据库，模拟旧索引落后 | 读取受 session/知识库 UUID/存储指纹/revision 限制；索引候选回 PostgreSQL 核验 |

**先测修复失败，再测真实五轮。** 只证明“生成会拦住通知”或“修复成功一次”不足以证明失败闭环。故障注入均在隔离库，不修改主库、主 Qdrant 或真实用户会话。

## 6. 预算、Prompt、质量和性能

### 6.1 容量硬检查

规划、生成、门控及局部修复分别计算：`实际输入估算 + 输出预留 + 安全余量 <= 经核实的服务端上下文上限`。输入包括 system/user、Schema、历史、证据、引用、JSON/工具格式开销；输出检查服务端及应用阶段上限。生成前以最坏候选长度预检后续门控。记录本地估算、实际 HTTP `max_tokens`/thinking、供应商 usage、`finish_reason`、修复/重试次数及估算误差；usage 缺失记 unknown，不计零。

现行实现参数作为**待核验配置**：65,536 上下文、4,096 安全余量；生成输出预留 20,480、门控输出预留 4,096；每题最多 4,096 UTF-8 字节、每批最多两题。方案零已观测最小生成输出余量 3,673 tokens、门控输出余量 2,048、生成/门控上下文余量 29,971/24,629。新批次仍须逐调用核对；验收目标为**生成输出余量 ≥1,536、门控输出余量 ≥2,048、生成与门控上下文预检余量各 ≥4,096 tokens**。这些是应用预检安全门槛，不是供应商计费或容量承诺；若实际供应商限制更低，先调整配置并重新冻结。

### 6.2 答案和 Prompt 双层审查

- 逐题人工对照 gold 检查目标覆盖、事实/引用支持、条件与否定约束、语言/格式、数值、环境隔离及 `waiting_input`/`no_evidence` 的区分。部分成功必须在最终回复明确呈现；状态为 `answered` 不等于质量通过。
- 抽查生成阶段最终 messages：当前问题是否自足，必要历史/条件是否完整，旧助手回答是否被误作证据，是否塞入长账本，证据是否与题号/版本一致，Schema 与输出长度是否足够。Prompt 缺陷与生成缺陷分开归因。
- 使用 LlamaIndex `BatchEvalRunner` 配合 `ContextRelevancyEvaluator`、`CorrectnessEvaluator`、`RelevancyEvaluator`、`FaithfulnessEvaluator` 评分**已保存的测试输出**，不为评分重新生成会话。`DatasetGenerator` 只协助起草候选，gold 须人工核验冻结。报告列评估器模型、调用和 usage。身份、覆盖、引用权限、数值与提交状态由程序及人工检查，不能由评估器代判。
- 旧误拒 MT15、MT31、MT36/U1 使用原来源/候选复验；门控每题决策与人工真值对照，分别计算误拒和误放；“不得通知”与建议执行通知分别标注。

### 6.3 延迟、资源与存储

在 C/E 关口分别统计规划、历史定位、Embedding、Qdrant、BM25/RRF、Reranker、上下文组装、生成、门控、提交、索引更新耗时 P50/P95，以及整轮端到端 P50/P95；记录样本数、首正文时间和并发度。嵌套阶段耗时不能直接相加。每位置记录 API 调用次数、输入/输出/推理 tokens、重试及 unknown usage；不设金额上限，但调用须可审计。

固定采样计划间隔（建议 1 秒）并保存**实测**间隔、缺测数和采样器开销。分别报告 Python RSS/Private Bytes、LM Studio、Qdrant、PostgreSQL 进程或服务口径及本地 GPU 显存；整卡显存含其他应用，RSS 的共享页可能重复计入。记录每轮 PostgreSQL/派生索引新增字节、证据映射数、日志与诊断文件增长及正文/向量复制检查。延迟和内存**先采真实基线再冻结绝对上限**，不可把旧 CPU+Chroma 诊断耗时当新会话 SLA。

## 7. 通过标准与报告

**硬性阻断：**确定性契约、阶段参数、失败恢复和隔离断言必须全部通过；任何跨会话/跨库读写、未经授权引用、静默漏题/误合并、关键禁止动作进入可见回复、违规候选提交、错误 revision/重复提交均使整体验收失败。方案零五轮逐轮 gold 全部通过；第四轮禁止通知和第五轮工单/草稿隔离不能由平均分抵消。`length`/空正文不得标记业务成功。

**建议语义质量门槛（首次真实 C 批次冻结为正式门槛）：**已人工确认可回答的子题，必要证据 Top-K 覆盖率建议 ≥95%，人工逐题答案合格率建议 ≥95%；同时单列无依据/待补分类准确率、门控误拒/误放、原目标覆盖率及错误合并率。分母只含 gold 冻结且该知识快照确有依据的题；不把无参考来源的题当检索失败，也不因总体 ≥95% 放过硬性阻断项。重复运行逐次检查关键门槛，报告均值和波动，不只报最优一次。

每个测试项只标 **通过 / 失败 / 阻塞 / 未运行**，跳过或依赖不可达不可计通过。整组报告至少包含：运行 ID、Git SHA、环境/知识快照、原文与 gold 版本、请求位置及任务数、逐题结果/来源、Prompt 审查、预算和真实 HTTP/usage、P50/P95/资源/存储、故障注入前后账本、历史 Bug 映射、人工复核者及未关闭问题。私有原始诊断与汇总 Markdown 分开存放；失败运行不覆盖，复测使用新运行 ID。

执行顺序：先补禁止动作专项三连测及 72 定向契约，再复跑方案零真实五轮；接着跑真实知识链与 L01–L12，随后故障注入与稳定性测量；最后依据**最终可见答案**逐题签署结论。原单轮 `query` 的零 LLM 输入预览及既有 128+128 检索基准作为独立回归记录，不与 43 个多轮请求位置混算。
