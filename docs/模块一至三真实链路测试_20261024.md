# 模块一至三真实链路测试：方案 0 子问题连接

> 历史资料说明（2026-11-06）：以下设计、实施过程、基线与验收结果按文中原日期保留，不作为当前功能状态或可直接执行的部署步骤。当前说明见[文档导航](README.md)。本次未重新运行原验收，也未把历史失败改成通过。

日期：2026-10-24（Asia/Shanghai）。分支：`feature/conversation-ledger-v12`。

## 验收结论

**历史对象选择方向符合方案 0，但实时五轮完整链路尚未通过验收。**

两批真实调用都未连续提交完五轮：第一批到 revision 4，第五轮因诊断连接器的只读引用 Schema 失败；修正该约束后，第二批到 revision 2，第三轮因模型重复输出同一历史对象的修订条目失败。不能将不同批次的成功轮次拼成一次端到端通过。

另将第一批每轮最后一次真实模型返回原样回放，在新隔离 PostgreSQL 中达到 revision 5。这个零 API 回放证明修正只读引用契约后，已有真实返回能被模块三执行并提交，**不代表模型重新调用能够稳定通过**。回放还暴露第四、五轮过度判定缺失信息的问题。

## 范围与测试方式

唯一业务输入为 [方案 0 五轮原文](多轮询问模块重建子方案/00-唯一连续回归用例.md)，逐轮、同会话执行。预期表只用于离线验收，不进入模型 Prompt。

实际诊断链路：

```text
原始用户消息
→ 模块一：认领请求、绑定会话和 revision
→ 模块二：真实 TaskPlanningPipeline.plan
→ 诊断连接器：读取本会话已提交问题目录，LLM 选择历史别名及条件修改
→ 程序核验别名、身份、版本、来源和任务覆盖
→ 模块三：resolve / prepare_batch
→ 模块一：commit_request
→ 导出实际题号、对象版本、条件变化及剩余缺口
```

- 原业务 Workflow 尚未连接三个模块。本次新增的 `scripts/phase0_history_probe.py` 是测试编排和诊断适配器，不是方案六生产 Workflow 或 HTTP/CLI 会话接口。
- 模块二仍只解析当前消息；历史候选由诊断连接器在限定 session、库 UUID、指纹和 revision 后读取，真实模型决定本轮任务与候选的关联。没有人工预置 Q1/Q2/Q3 选择器。
- 同一计划任务可关联多个历史对象；同一对象一次只接受一个修订条目。当前适配器拒绝重复条目，并允许一次模型结构修复，不默默取其中一条。
- 模块三暂未提供“新增缺失输入”的参数；适配器显式把经原文校验的缺失项写入待提交 question draft。此边界不是现有生产接口已集成的能力。
- 使用现有 LlamaIndex `structured_predict`、Pydantic Schema 和回调；回放使用原生 `PydanticOutputParser`。模型为 `deepseek-flash`，诊断进程关闭 thinking，输出上限 16,384，temperature=0，供应商自动重试 0，每个解析/关联阶段最多两次结构尝试。业务永久配置未修改。
- 没有生成助手回答。因此只能验证用户目标、历史对象和条件延续，不能验证对“上一轮回答内容”的忠实继承，也不评价答案质量。
- 没有调用知识检索、Embedding、Reranker、Qdrant 或业务写操作。三次运行分别使用新建隔离 PostgreSQL 实例，结束后均已停止，原有库和旧报告保持原状。

## 后续修复优先级

1. 先确定同一历史对象的多任务归并契约：相同操作、无冲突的字段和来源由程序去重合并；有冲突时保留错误并聚焦修复，不能随机选取一条。
2. 区分“阻断诊断的必要资料”“某个独立子目标所需资料”和“非必要实施细节”；清除已被当前记录解决的缺口，避免一个可选细节阻塞整组任务。
3. 从对象有效版本生成独立问题，明确历史条件已被替换；保留来源链供审计，避免把旧条件全文不断追加给下游。
4. 把经确认的诊断连接契约纳入正式编排，并补齐技术失败状态与恢复；再重新运行同一份方案 0 的实时五轮验收。
